# Pesquisa de mercado no GitHub: plataformas Web GIS e mapas de campus

**Escopo:** repositórios públicos reais com mapa interativo, publicação/edição de dados geoespaciais, PostGIS, WMS/GeoServer e/ou controle de acesso.

## Método e consultas

A busca feita com o GitHub CLI (`gh search repos` e `gh api`), usando as consultas:

```text
campus map GIS
web GIS PostGIS GeoServer
collaborative map editor PostGIS
GeoServer RBAC web GIS
umap
geonode
MapStore2
lizmap
geoserver
```

Depois da busca, foram inspecionados metadados via API, README, árvore do repositório e, quando disponíveis, `docker-compose.yml`, `pyproject.toml`, `package.json` e documentação. As estrelas/forks abaixo são o retrato retornado pelo GitHub API durante a pesquisa; não são medida de qualidade.

## Padrões de arquitetura identificados

1. **Separação entre aplicação e serviço cartográfico.** GeoNode, MapStore e Lizmap não tratam o navegador como fonte de verdade: a aplicação gerencia usuários, projetos e configuração, enquanto GeoServer/QGIS Server publica os dados por OGC.
2. **PostGIS como persistência espacial.** GeoNode e uMap declaram PostGIS no Compose; MapStore também fornece Compose com imagem PostGIS. Isso valida o uso de PostgreSQL/PostGIS como base oficial das features colaborativas.
3. **OGC como contrato de integração.** WMS é adequado para visualização renderizada; WFS/OGC API - Features é mais apropriado quando a edição ou consulta de geometria precisa ser interoperável. GeoServer documenta ambos explicitamente.
4. **Autorização em camadas.** GeoNode oferece compartilhamento de recursos e grupos; MapStore demonstra LDAP/Keycloak; GeoFence acrescenta regras finas por camada, atributo, área e filtro. A complexidade cresce rapidamente além de `public/editor/admin`.
5. **Compose para ambientes reproduzíveis.** Os repositórios maduros mantêm serviços, volumes, health checks e configuração de autenticação explícitos. Isso é útil para o desenvolvimento local, mas não significa que toda a stack precise entrar no primeiro incremento.
6. **Edição precisa de um contrato de domínio.** uMap/Lizmap mostram a experiência de edição; GeoNode mostra catálogo e permissões. Nenhum deles, por si só, deve ser copiado como modelo completo do fluxo específico “contribuição pendente → revisão → aprovação” da UFAM.

## Aplicação ao Campus Map UFAM

O PRD/ADR local já escolhe TypeScript, Next.js/OpenLayers, API Node/Express e PostgreSQL 16/PostGIS 3.4, deixando GeoServer para depois. A pesquisa reforça essa decisão para o MVP:

- manter **PostGIS + API própria** como fonte oficial das features e do estado `pending/approved/rejected`;
- implementar primeiro o RBAC mínimo (`public`, `editor`, `admin`) e a aprovação transacional no backend;
- usar **OpenLayers + GeoJSON** para edição inicial, aproveitando a ergonomia de edição observada em uMap/Lizmap;
- encapsular uma futura publicação em GeoServer atrás de uma interface própria, sem acoplar o domínio aos endpoints REST do GeoServer;
- quando necessário, publicar camadas aprovadas via WMS/WFS/OGC API e avaliar MapStore para um visualizador avançado, ou Lizmap/QGIS Server se a produção cartográfica continuar centrada em projetos QGIS;
- tratar trilhas, árvores, edificações e áreas florestadas como camadas de domínio com formulários e validações próprios, em vez de aceitar um esquema genérico de CMS GIS;
- considerar GeoFence/Keycloak somente quando houver necessidade comprovada de autorização por área, atributo, unidade acadêmica ou múltiplos serviços.

## Riscos, limitações e licenças

- **Licenciamento:** GeoNode declara GPLv3 no README; GeoServer e GeoFence são GPL (GeoFence explicita GPLv2); Lizmap permite MPL 2.0/GPLv2/LGPL 2.1; MapStore declara BSD simplificada. O metadata do GitHub para GeoNode, MapStore e uMap aparece como `NOASSERTION`/“Other” em alguns casos; confirmar os arquivos de licença e obrigações de distribuição antes de incorporar código, não apenas executar serviços.
- **Custo operacional:** GeoNode/MapStore/Lizmap adicionam serviços, versões e observabilidade. Isso pode ser desproporcional ao primeiro release e aumentar o risco de incompatibilidade entre GeoServer/QGIS Server, Java/PHP, plugins e banco.
- **Segurança de demonstração:** o README do MapStore usa `admin/admin` no quick start; isso é aceitável apenas localmente. Segredos, credenciais padrão e exemplos de Compose não devem chegar a produção.
- **Autorização não é aprovação:** ACL de camada (GeoNode/GeoFence) controla quem pode ler/usar dados; não substitui o workflow de revisão, auditoria e autoria exigido por uma contribuição colaborativa.
- **Edição via OGC:** WFS-T/edição por servidor exige cuidado com validação, concorrência, permissões e versionamento. Não deve ser habilitado apenas por haver WFS disponível.
- **Dependência de dados externos:** basemap OSM, imagens, WMS e SVI têm políticas, disponibilidade e limites próprios. A aplicação deve manter fallback e registrar atribuição/termos de uso.
- **Busca de campus:** `gh search repos "campus map GIS"` retornou principalmente o [IIT Dharwad Campus Map GIS](https://github.com/harshmeena010/IIT-Dharwad-Campus-Map-GIS-), um artefato de mapeamento sem evidência, no README/estrutura inspecionada, de plataforma web colaborativa com PostGIS/RBAC. Por isso ele não foi usado como referência arquitetural.

## Recomendação objetiva para iniciar

**Iniciar com a arquitetura já registrada no ADR local: API Node/Express + PostGIS + OpenLayers, sem GeoServer no primeiro slice.** Implementar uma única fatia vertical: mapa público, login, criação de feature pelo editor, persistência como `pending`, fila administrativa e aprovação que passa a expor a feature publicamente. Usar uMap/Lizmap como referências de interação de edição, GeoNode como referência de catálogo/permissões e GeoServer/GeoFence como opções de uma fase posterior.

O primeiro experimento de integração recomendado, depois do fluxo aprovado estar estável, é publicar **uma camada somente leitura** de features aprovadas via GeoServer/WMS e comparar desempenho, cache, estilo e custo operacional com o GeoJSON servido pela API. Só migrar a fonte de leitura/edição para serviços OGC se esse experimento resolver uma necessidade concreta de interoperabilidade, volume ou cartografia institucional.
